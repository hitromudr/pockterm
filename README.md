# pockterm

[English version](README.en.md)

Карманный терминал: мобильная PWA-окно к твоим tmux-сессиям, которое
раздаёт один Go-бинарник. Удобно управлять с телефона любой консолью —
например [Claude Code](https://claude.com/claude-code) или любым TUI.

- **Один бинарник.** Статика PWA встроена; на хосте нужен только `tmux`.
- **Настоящий терминал.** xterm.js поверх моста WebSocket→PTY, плюс
  панель клавиш (Esc, Tab, стрелки, залипающий Ctrl) для мобильных
  клавиатур.
- **Список и подключение.** pockterm показывает запущенные tmux-сессии
  и присоединяется к выбранной. Он **не создаёт** сессий сам — ты
  запускаешь их на сервере как обычно.
- **Grouped-сессии tmux.** У каждого клиента свой размер экрана: телефон
  не сжимает окно tmux на ноутбуке.
- **Кнопки ответа.** Интерактивное меню (например, запрос разрешения
  Claude Code) распознаётся по маркеру выбора и рамке, а не по любой
  нумерации, поэтому нумерованный список в тексте кнопок не создаёт.
  Пока экран прокручен в историю (copy-mode), кнопки скрыты.
- **Обмен с буфером.** Кнопка ✂ включает режим выделения: свайп
  перестаёт прокручивать, текст выделяется системно, кнопки Copy и
  Paste переносят его в буфер устройства и обратно в терминал.
- **Картинка из буфера.** Скриншот вставляется тем же Paste (или Ctrl+V,
  или перетаскиванием файла): в pty пролезают только нажатия клавиш,
  поэтому картинка уходит на сервер, ложится файлом рядом с кэшем
  пользователя, а в терминал печатается путь к ней — то, что агент и так
  умеет читать.
- **Сессии из интерфейса.** `+` создаёт по готовому пресету (`shell`,
  `claude`, `yolo`, `continue`), `✎` переименовывает, `✕` закрывает в два
  касания. Команду страница не передаёт — только имя пресета; запускает всё
  тот же Makefile, которым пользуются руками. Нужно потому, что с телефона,
  где не осталось ни одной сессии, создать её было нечем.
- **Уведомления в Telegram.** Сервер сам смотрит на экран сессии через
  `capture-pane` и пишет в чат, когда агент просит ответ или затих. Это
  работает при закрытом pockterm — то есть тогда, когда и нужно.

## Быстрый старт

```bash
make build
./bin/pockterm
# запусти сессию: tmux new-session -d -s work
# открой http://127.0.0.1:8130 и выбери её
```

## Установка на сервер

```bash
git clone https://github.com/hitromudr/pockterm && cd pockterm
sudo bash deploy/install.sh        # или: make install
```

Скрипт собирает бинарь, кладёт его в `/usr/local/bin`, генерирует токен в
`/etc/pockterm/pockterm.env` (права 600), пишет systemd-юнит и запускает
сервис от того пользователя, чьи tmux-сессии нужно обслуживать — под `sudo`
это тот, кто его вызвал. Повторный запуск ничего не ломает: токен
сохраняется, юнит перезаписывается только при изменении. Удалить —
`sudo bash deploy/install.sh --uninstall`.

Сервис слушает loopback. Чтобы попасть на него снаружи, поставьте впереди
обратный прокси — готовые примеры лежат рядом:

| Файл | Когда |
|---|---|
| `deploy/nginx-token.conf.example` | TLS плюс встроенный токен. Быстро начать |
| `deploy/nginx-mtls.conf.example` | Клиентские сертификаты. Держать долго |

Если впереди mTLS, токен не нужен и только мешает: сервер начнёт отвечать
`401` на ссылку без него, а выглядит это в браузере как машина без сессий.
Ставьте с `POCKTERM_NO_TOKEN=1`:

```bash
sudo POCKTERM_NO_TOKEN=1 bash deploy/install.sh
```

Уже выданный токен установщик при этом не трогает — только предупреждает.

Токен в адресной строке попадает в историю браузера и в логи прокси, поэтому
для постоянной установки предпочтительнее mTLS: там сканер интернета видит
отказ в рукопожатии, а не страницу входа. Инструкция по выпуску сертификатов
и установке их на телефон — в шапке `nginx-mtls.conf.example`.

## Подключение телефона

```bash
make qr PUBLIC_URL=https://pockterm.example.com
```

QR-код печатается прямо в терминал: наведите камеру — откроется адрес вместе
с токеном. Дальше «Добавить на главный экран», и pockterm ведёт себя как
приложение: отдельное окно без вкладок, свои горячие клавиши.

Ту же ссылку можно получить без QR — `pockterm qr https://...` печатает и
код, и сам адрес.

## Конфигурация (окружение)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `POCKTERM_LISTEN` | `127.0.0.1:8130` | Адрес прослушивания. Не-loopback требует `POCKTERM_TOKEN`. |
| `POCKTERM_TOKEN` | пусто | Общий токен (`?token=...`); обязателен вне loopback. |
| `POCKTERM_TG_TOKEN` | пусто | Токен бота от @BotFather. Пусто — уведомлений нет. |
| `POCKTERM_TG_CHAT` | пусто | ID чата. Задаётся вместе с токеном, иначе старт откажет. |
| `POCKTERM_TG_LINK` | пусто | Ссылка, которую бот дописывает к сообщению (без токена). |
| `POCKTERM_TG_PREVIEW` | вкл | `off` — слать только факт и имя сессии, без текста с экрана. |
| `POCKTERM_TG_API` | `https://api.telegram.org` | Корень Bot API: локальный bot-server или тестовая заглушка. |
| `POCKTERM_IDLE` | `30s` | Сколько тишины считать завершением работы. |
| `POCKTERM_UPLOAD_DIR` | кэш пользователя | Куда сохранять вставленные картинки; `off` — выключить загрузку. |
| `POCKTERM_SESSION_DIR` | рабочий каталог сервиса | Где лежит Makefile с целями сессий (кнопка «+»); `off` — не давать создавать. |

## Создание сессий с телефона (кнопка «+»)

Команду страница не передаёт — только имя пресета (`shell`, `claude`,
`yolo`, `continue`), и сервер запускает `make -C <каталог> <пресет>`. Что
такое сессия, решает этот Makefile, а не pockterm: он же и остаётся
единственным местом, которое знает про песочницу, нумерацию и slice.

Готовый образец — `deploy/sessions.mk.example`:

```bash
cp deploy/sessions.mk.example ~/work/Makefile   # поправьте CLAUDE внутри
echo 'POCKTERM_SESSION_DIR=/home/youruser/work' | sudo tee -a /etc/pockterm/pockterm.env
sudo systemctl restart pockterm
```

Без `POCKTERM_SESSION_DIR` сервер ищет Makefile в своём рабочем каталоге —
для юнита это то, что сказано в `WorkingDirectory=` (в примере юнита и в том,
что пишет установщик, это домашний каталог пользователя). Makefile не найден
— кнопка «+» просто выключается, о чём сказано в журнале при старте.

## Уведомления

Под наблюдение попадает сессия, к которой хоть раз подключились через
pockterm; она остаётся под ним, пока жива. Сервер раз в две секунды
читает её экран через `capture-pane` и различает два события:

- **просит ответ** — на экране появилось интерактивное меню (одно
  сообщение на меню, не на каждый опрос);
- **закончил** — экран не менялся `POCKTERM_IDLE` после того, как
  что-то происходило.

**Решение одно, каналов два.** Событие уходит в Telegram и тем же кадром
по вебсокету — открытой странице, которая покажет системное уведомление
(в приложении — через мост, в браузере — через Notification API). Раньше
страница решала сама, и это была ошибка: она считала активностью любые
байты из сокета, а tmux перерисовывает строку статуса по часам, так что
отсчёт тишины почти не доходил до конца; проверял его таймер, который
Android в свёрнутом WebView душит до одного срабатывания в минуту.
Приходило непонятно что и непонятно когда. Сервер читает панель
напрямую — без строки статуса и без троттлинга.

Пока сессия открыта в pockterm и вкладка на экране, уведомления по ней
молчат: ты и так всё видишь. Свёрнутая PWA держит сокет открытым, но
считается невидимой — сообщение придёт. Если система усыпит и сам сокет,
до страницы кадр не дойдёт; Telegram в этом случае остаётся.

Текст короткий и одинаковый в обоих каналах: заголовок называет сессию
(`✅ claude-1 закончил`), в теле — последняя осмысленная строка панели.
Именно осмысленная: снизу у агентских TUI нарисована рамка ввода и
подсказка про шорткаты, и «последняя непустая строка» — это они.

ID чата проще всего узнать так: написать боту любое сообщение и открыть
`https://api.telegram.org/bot<токен>/getUpdates`.

## Развёртывание

Сам pockterm слушает loopback. TLS и аутентификацию (клиентские
сертификаты или встроенный токен) обеспечивает обратный прокси перед
ним. Пример systemd-юнита — `deploy/pockterm.service.example`.
Прокси обязан пропускать WebSocket-upgrade для `/ws` и отключать
буферизацию. Прокси также обязан сохранять заголовок Host в исходном виде
(nginx: `proxy_set_header Host $host;`) — сервер сверяет `Origin` с `Host`
запроса и отклоняет апгрейд, если прокси его переписывает.

## Обновление без разрыва работы

Установка нового бинарника перезапускает юнит, а в нём сидит тот, кто этим
терминалом пользуется. Чтобы не выбирать между свежей сборкой и целым
сеансом, `deploy/pockterm-deploy` спрашивает у работающего сервера
`/api/presence` и ставит только тогда, когда страницу никто не смотрит:

| Файл | Что делает |
|---|---|
| `deploy/pockterm-deploy` | проверяет подпись, ждёт паузы, ставит, откатывает |
| `deploy/pockterm-deploy.path` | замечает появление сборки |
| `deploy/pockterm-deploy.timer` | повторяет попытку раз в минуту, пока идёт работа |
| `deploy/pockterm-deploy.service` | запускает скрипт |

`/api/presence` отвечает `{"clients":N,"visible":M}`: `clients` — открытые
сокеты, `visible` — вкладки на экране. Ждут именно `visible`: свёрнутая PWA
держит сокет часами, и по нему паузы не дождаться. Сервер, который не
ответил, считается свободным. `FORCE_AFTER` (по умолчанию 6 часов)
ограничивает ожидание, одинаковые байты перезапуска не вызывают, а
не поднявшийся бинарник откатывается на предыдущий.

Схема рассчитана на CI, который кладёт подписанный файл в
`/var/lib/pockterm/incoming`; ключ подписи нужен потому, что этот каталог
виден сборочной задаче. Проверить скрипт, ничего не трогая на машине:
`make test-deploy`.

## Модель безопасности

pockterm отдаёт полный терминал любому, кто подключился. Относитесь к
нему как к SSH: не выставляйте наружу без TLS и аутентификации.
Бинарник отказывается слушать не-loopback адрес без токена.

Уведомления отправляют кусок экрана во внешний сервис: строку вопроса и
пункты меню либо последнюю строку вывода. Объём ограничен (не больше
восьми пунктов, строки режутся по 200 символов), но содержимое сессии
всё равно покидает хост. `POCKTERM_TG_PREVIEW=off` оставляет только факт
события и имя сессии. Ссылка в сообщении токена не содержит.
